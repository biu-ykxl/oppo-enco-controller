# 真机验证记录 —— OPPO Enco Free4 丹拿版（`06C010`）

环境：Windows 11 / 耳机 `AA:BB:CC:DD:EE:FF`（已隐去真实地址） / 蓝牙音频已连接 / 无欢律占用。
下面所有报文均为真实抓取，ack 状态字节 `00` = 成功。

## 1. 连接

| 项 | 结果 |
|---|---|
| RFCOMM 通道 | **15**（0.14s 直连）；12 与 1..30 作兜底扫描 |
| 通道有效性 | 连上后发电量查询，收到 `0x8106` 才认定是控制通道 |
| 产品 ID `0x0103` | `00 10 C0 06` → **06C010**（丹拿版） |
| 固件 `0x0105` | `1,2,118 / 2,2,118 / 3,1,105` → 左 118、右 118、盒 105 |

> 通道 3（HFP）也曾接受连接，但所有命令静默超时 —— 这就是必须做应答校验的原因。

## 2. 降噪（`0x010C` / `0x0404`）

查询请求 `01 01`，回复 `status + 2 字节回显 + 状态位图`；位索引是**叶子档位 ID**。

| 发送 index | 回复位图 | 实际生效 |
|---|---|---|
| 0 / 3 | `08 00` | 3 关闭 |
| 1 / 6 | `40 00` | 6 轻度降噪 |
| 2 / 8 | `00 01` | 8 通透 |
| 4 | `10 00` | 4 深度降噪 |
| 5 | `20 00` | 5 中度降噪 |
| 7 | `80 00` | 7 智能降噪 |
| 11 | `00 08` | 11 智能自适应 |
| 9 / 10 | `00 02` | 9（语义未标注） |
| 12 | `00 08` | 回退到 11 |

`0x0404` 的 ack 恒为 `00`，不能作为成功依据，必须回读 `0x010C`。

## 3. 音效（`0x0122` / `0x0406` / `0x010F`）

`0x0122` payload `01 05`，回复 110 字节、count=3，条目布局
`[selected][min][max][eqId][nameLen][name UTF-8][bandCount][(freq LE16, gain int8)*]`：

| eqId | 名称 | 六段增益 |
|---|---|---|
| 4 | 均衡耐听 | 62Hz+2 · 250Hz−1 · 1k+4 · 4k+2 · 8k+0 · 16k+3 |
| 5 | 人声凸显 | 62Hz−4 · 250Hz+3 · 1k+2 · 4k−2 · 8k+3 · 16k+0 |
| 6 | 声场增强 | 62Hz+1 · 250Hz+4 · 1k+6 · 4k+3 · 8k+0 · 16k+1 |

- min/max 实测 `0xFA`(−6) / `0x06`(+6)，增益为有符号字节。
- 切换 `0x0406 [id]` → ack `00`，`0x010F` 回读 4/5/6 全部一致。
- **`0x0122` 只返回具名/自定义预设**，内置 0~3 不在此列表，界面做合并去重。

## 4. Hi-Res / 码率（`0x0403` feature `0x18`）

| 载荷 | ack | 结果 |
|---|---|---|
| `18 00` | `00` | 标准码率 |
| `18 02` | `00` | Hi-Res 高清 |
| `18 01` | 无 ack | **耳机断开 RFCOMM（10053）** |
| `18 03` | 无 ack | **再次断链** |

结论：`0x18` 是枚举 0/2，不是布尔；其余值会让耳机踢掉链路。
白名单 `spatialHiResMutex`（空间音频与 Hi-Res 互斥）印证其语义。

### 码率为什么读不到

- 扫遍设备声明的 25 个 `0x01xx` 查询：无一返回编码/码率。
  `0x0107` = `00 02 01 03 02 00`、`0x0109` = `00 03 01 04 02 07 03 04`、`0x0114` = `00 02`，
  官方 SDK 里前两条同样是「未解析轮询」。
- `Get-PnpDeviceProperty` 查 A2DP 节点：无 codec / bitrate 属性。
- 可用的是 Core Audio `GetMixFormat`（`oppo/audioinfo.py`）：实测 `48000 Hz / 32-bit float / 2ch`，
  这是主机混音格式、不是蓝牙码率，界面如实标注、不伪造 kbps。
- 真实码率由主机编码决定：Windows 只协商 SBC/AAC（约 200~330 kbps）。

## 8. 2026-11-14 修正与 realme

### 8.1 「模式 2/13/16/18/19/22/23」是误解析

Free4 不支持档位查询：`0x010C` + `03 01` 返回 **`02 16 0C 20 11`**（status=0x02 = 拒绝），
后面几个字节是状态数据而非位图。此前直接按位图解析，于是出现了「模式 13」这类假档位。

现在：status 非 0 即放弃发现，只接受 status=0 且档位落在 0..11、数量 1..8 的结果。
Free4 实测 `anc_modes()` 返回 `[]`，界面回退到型号档案的 7 档（正确）。

### 8.2 realme Link 协议（据公开抓包实现）

帧结构与本项目一致（`aa | len | 00 00 | cmd | seq | plen | payload`，
realme 文档把长度写作 2 字节 LE，短帧下与 1 字节 varint 等价）。
本项目的 `frame()` 对三条 ANC 命令的产出与抓包**逐字节相同**：

| 模式 | 抓包/本项目输出 |
|---|---|
| 普通 | `aa0a00000404010300010101` |
| 通透 | `aa0a00000404010300010102` |
| 降噪 | `aa0a00000404010300010108` |

要点：ANC 值 `01/02/08`（位 0/1/3）；读 ANC `0x010C` payload `01 01` → `00 01 01 [MODE]`；
**读单个功能状态** `0x010D` payload `01 <id>` → `00 01 <id> <state>`；
写功能 `0x0403 [id] [0/1]`；游戏模式 feature 为 `0x06`(T310) / `0x08`(T300)；
通道 1(T310)/10(T300)。

### 8.3 顺带验证（Free4 真机）

- 7 个 ANC 档位正常生成，无不存在的档位；
- 条状文字按钮点击轮转，面板同步高亮所读回的档位（通透 → 智能自适应）；
- 分区收起后窗口高度 860 → 712。

## 9. 真断开 / 自动连接（2026-11-15）

Windows **没有公开 API** 可以「断开但不取消配对」。实测两条底层路径：

| 方案 | 结果 |
|---|---|
| `IOCTL_BTH_DISCONNECT_DEVICE`（`0x41006C`，对 radio 句柄发 DeviceIoControl） | 本机驱动返回 **WinError 50（不支持）**，仅作兜底 |
| `BluetoothEnumerateInstalledServices` + `BluetoothSetServiceState(DISABLE)` | **可用**：停用 5 项服务后，链路在 1 秒内断开 |

重新连接用 `BluetoothSetServiceState(ENABLE)` 依次开 A2DP / HFP / AVRCP，
实测 1 秒内链路恢复。两者都保留配对。

实现要点：
- 断开前先关掉本程序的 SPP 套接字，否则链路可能被占用而不断；
- 服务已全部停用时再「断开」返回「本就未连接」，UI 视为成功；
- 结果通过 Qt Signal 回到 GUI 线程，不能在工作线程里直接改控件。

自动连接：记住上次设备地址与「启动时自动连接」开关（QSettings），
启动后 0.5s 自动选中该设备并连接；若链路不在，先拉起 A2DP 再开控制通道。

真机验证：启动自动连接 → 已连接；点断开 → 链路 False；点连接 → 链路 True。

## 10. 断开提速与「重连后掉线」修复（2026-11-15 01:40）

### 10.1 只停 A2DP 就够，别停全部服务

| 做法 | 耗时 | 副作用 |
|---|---|---|
| 停用 3 项服务（A2DP/AVRCP/HFP） | **9.4s**（每项 3.1s 同步阻塞） | 重连时只恢复部分服务 → **连上就掉线** |
| 只停 A2DP | **3.1s** | 无；HFP/AVRCP 保持启用，回连稳定 |

实测：A2DP 停用后链路立刻释放，无需再动其它服务。这同时是「重连后断联」的根因——
之前把服务全停了，重连只按固定 GUID 恢复 3 项，漏掉的（如 SPP）一直是禁用状态。

### 10.2 其它导致掉线的坑

1. **`is_connected()` 用枚举缓存会滞后**：断开后 `BluetoothFindFirstDevice` 仍报
   `fConnected=True`，导致重连时误判「已连接」而跳过拉起链路 → 有声音通路没有、SPP 起来后又掉。
   改用 `BluetoothGetDeviceInfo` 实时值。
2. **两个会话线程抢一只耳机**：重连重试时旧线程没停就起新的，两个 SPP 互踢。
   现在重试前 `shutdown()` + `join()`，并给事件加来源校验，旧会话的回调直接丢弃。
3. **QWidget 在子线程创建**：会话的信号桥原来是 QWidget，自动连接在子线程里创建它，
   信号投递失败 → UI 永远停在「自动连接…」。改为 QObject，且会话统一在 GUI 线程创建。
4. **断开前必须关掉 SPP 套接字**：ACL 被我们的 SPP 占着时，停音频服务也断不掉。
   现在直接 `sock.close()`（不等锁）+ `join(0.8)` 后才停服务。

### 10.3 最终实测

| 动作 | 结果 |
|---|---|
| 点击断开 → UI | 立即显示「已断开」 |
| 链路真正释放 | 3.1s |
| 点击连接 → 已连接 | 4.0s（SPP 与 A2DP 并行拉起） |
| 重连后稳定性 | 25s 内无掉线 |
